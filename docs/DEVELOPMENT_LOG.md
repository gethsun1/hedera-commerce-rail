Each agreement is HBAR-only (`asset == address(0)`), created unfunded, funded exactly once by its payer, and finalized by release or refund. Payer or configured arbiter can release; payer can refund only strictly after deadline; arbiter can refund as dispute resolution. Funding is rejected at/after deadline. There is no cancellation, milestone logic, HTS transfer, HCS write, frontend, or deployment execution. Events expose payment ID, parties, amount, asset marker and relevant timing. `PaymentEscrow` is tagged for explicit Hardhat deployment.
- **Security model:** Uses the already installed OpenZeppelin `ReentrancyGuard`; updates state and tracked liabilities before checked external value transfer, relying on transaction revert to restore state if the recipient rejects. Invalid IDs/addresses/amounts/deadlines, unauthorized actors, incorrect value, invalid state transitions, and direct unaccounted deposits revert with custom errors. `totalEscrowed` tracks funded liabilities; forced surplus cannot be treated as escrow liability. Arbiter is trusted to resolve a payment honestly and must be selected accordingly.

## 2026-10-03 — Milestone 5: HCS audit/event integration

- **Research:** Reviewed current Hedera Native SDK docs for [topic creation](https://docs.hedera.com/native/consensus/create-topic), [message submission](https://docs.hedera.com/native/consensus/submit-message), and [Mirror Node topic endpoints](https://docs.hedera.com/reference/rest-api/topics); verified maintained Hiero JavaScript SDK transaction classes in the installed `@hiero-ledger/sdk` 2.89.1. A topic gets a numeric topic ID from the create receipt; omitting a submit key makes it public, while an absent admin key prevents administrative deletion/config changes. HCS receipts expose the updated topic sequence; Mirror Node records ordered messages and consensus timestamps. Each message incurs standard network fees, and optional topic custom fees are not enabled here. Message size is limited to 1,024 bytes per chunk; the schema rejects oversized single-event payloads.
- **Event source and schema:** Kept existing `PaymentEscrow` / `TokenPaymentEscrow` logs as source of truth. `normalizeEscrowLog` recognizes their Created/Funded/Released/Refunded event families and combines receipt coordinates with a resolved payment snapshot (payee is not present on every lifecycle log). Schema v1 provides payment event type, decimal-string payment ID/amount/block, asset type and optional HTS token EVM address, parties, escrow address, network, source tx hash/log index, occurrence time, and scalar metadata. No private application data belongs in metadata.
- **Publisher and consistency:** Added a server-side publisher using the already-installed Hiero SDK. Runtime topic ID/network/operator are explicit environment config; topic creation is a separate opt-in Testnet script, never app startup. SDK precheck, receipt, configuration, and network errors propagate. Same-process concurrent submissions are coalesced and a successful event ID cannot be resubmitted again by that publisher instance. There is no durable outbox/deduplication store or cross-process exactly-once guarantee. On ambiguous timeouts a caller retry can duplicate a published message; consumers use SHA-256 `eventId` over network, normalized source transaction hash, contract address, and log index to deduplicate. Settlement does not call HCS and is not rolled back by HCS failure.

Updated the existing Hiero configuration helper to explicitly parse raw 32-byte secp256k1 hex with `PrivateKey.fromStringECDSA` (and DER/ED25519 encodings explicitly).
