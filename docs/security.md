# Security and production notes

This project has received a security-focused code review and targeted hardening. It has not been formally audited, penetration tested, or certified for production. Deployers must review the exact source, configuration, and deployed bytecode they operate.

## Secrets and operators

- Keep account private keys, HCS submit keys, RPC credentials, and signing material in a secret manager or runtime-only environment. Never commit `.env` files or prefix credentials with `NEXT_PUBLIC_`.
- Example environment files contain names and placeholders only. Treat local `.env` files as sensitive; do not include their values in logs, support requests, build artifacts, or generated scaffold output.
- Use a dedicated, least-privileged operator account for server-side HCS publication. Protect and rotate it operationally. A compromised HCS publisher can submit misleading public audit messages to an open topic, but cannot change escrow state.
- Deployment keys can deploy or administer whatever privileges their account has. Keep deployment credentials separate from application and user-wallet signing keys.

## Wallet and trust boundary

The browser entry (`@hedera-commerce/sdk/browser`) accepts an external wallet signer and includes settlement support only. It does not load the Hiero SDK or server HCS publisher. The server entry (`@hedera-commerce/sdk/server`) contains operator signing, HCS, and Mirror Node capabilities; keep it in server-only modules. The reference settlement UI asks the connected wallet to sign each transaction and checks Hedera chain ID 296. It has no operator-key fallback. A wallet user remains responsible for reviewing wallet prompts and addresses.

The Next.js audit route is server-only. It accepts a wallet signature over the Testnet transaction coordinates, verifies that the signer submitted the confirmed transaction, and checks the actual escrow event against RPC and Mirror Node data before publishing. HCS publication is an audit action after settlement; it cannot authorize or reverse settlement.

## Networks, amounts, and escrow limits

Testnet and Mainnet use distinct chain IDs (296 and 295). Select a live Hardhat network explicitly; deployments default to the local Hardhat network. Mainnet HCS publication requires an explicit opt-in. RPC and Mirror Node endpoint configuration is operator-controlled; Mirror Node endpoints must be HTTPS origins, redirects are rejected, pagination stays on the configured origin, and responses and request duration are bounded.

HBAR contract/SDK values are integer tinybars; Ethers transaction values are converted to weibars at the boundary. HTS values are integer token smallest units. No floating-point monetary conversion is supported. Token payer/payee accounts must meet Hedera association requirements, and payer allowance is required to fund HTS escrow.

Escrow supports payer or configured arbiter release, payer refund after the deadline, and arbiter refund at any time. A direct HBAR receive is rejected. HBAR forcibly sent through mechanisms that bypass `receive` can create an unaccounted surplus; it is not included in `totalEscrowed` and has no recovery method. HTS tokens sent directly to the contract similarly do not create a payment liability. Tokens with nonstandard/rebasing behavior are outside the supported fungible HTS model. A token transfer or recipient that cannot receive settlement can leave a funded payment unsettled until a valid transfer succeeds.

## Audit and indexing limits

HCS is at-least-once, not exactly-once. In-process duplicate suppression is not durable across process restarts; an ambiguous publish timeout followed by a retry can create duplicate messages. Consumers should deduplicate by deterministic event ID. There is no durable cross-process outbox. Mirror Node is eventually consistent and can lag consensus or return partial results; missing indexed data means “not observed yet,” not proof that a transaction failed. Contract state and successful transaction receipts remain settlement authority.

## Operations and residual risks

Use dependency lockfile review and vulnerability scanning in release automation; this repository has not upgraded dependencies broadly as part of hardening. Public RPC and Mirror Node services can rate-limit, lag, or become unavailable. Secure key storage, access controls, backups, rotation, monitoring, incident response, and deployment verification remain operator responsibilities. The reference application embeds demonstration Testnet contract/token addresses; replace and verify them when deploying another environment. No formal audit or production certification is claimed.

## Dependency security review (2026-10-04)

`npm audit` was run against the committed npm lockfile/workspace dependency graph. It reported 94 advisory package entries: 3 critical, 31 high, 38 moderate, and 22 low. These are audit findings, not 94 independently reachable application flaws. No dependency versions were changed in this review. The findings are retained and should be rescanned before releases; this project is not vulnerability-free.

The critical entries resolve to the Elliptic/Ethers v5 signing chain. The root `elliptic` 6.6.1 copy is patched for the critical malformed-message signing flaw; the affected copy is `zksync-ethers/node_modules/elliptic` 6.5.4, reached through `zksync-ethers` → Ethers 5.7.2 → `@ethersproject/signing-key` 5.7.0. The root Ethers 5.8.0 signing-key copy also resolves to patched root Elliptic 6.6.1 for that critical flaw. The vulnerable signing behavior requires the application to sign attacker-controlled malformed input with a vulnerable Elliptic key. The affected Ethers v5 chain is in the Hardhat/deployment tool graph, marked development-only in the lockfile; production application code imports Ethers v6. No production browser or server code invokes that v5 signing path. A separate low-severity Elliptic advisory still covers versions through 6.6.1.

The audit's aggregate `ethers` critical row also names `@hiero-ledger/sdk/node_modules/ethers` 6.16.0. This is not evidence that the Ethers v6 copy contains the vulnerable Ethers v5 signing-key chain: Hiero's Ethers 6.16.0 dependency does not depend on `elliptic` or `@ethersproject/signing-key`. The current/latest registry metadata for `@hiero-ledger/sdk` is 2.89.1 and pins Ethers 6.16.0 and `@grpc/grpc-js` 1.12.7 exactly. No compatible Hiero release with updated pins was available in this review, and no override or major SDK change was justified.

The 31 high-severity package entries classify as follows (versions and paths are from the lockfile audit):

- **Runtime transitive entries:** `@grpc/grpc-js@1.12.7` and aggregate `@hiero-ledger/sdk@2.89.1`; `postcss@8.4.31` under `next@15.5.27`; and `ws` copies `8.17.1` under Hiero, `8.18.0` under AppKit/WalletConnect, and `8.18.3` under viem. The gRPC findings concern server authentication context and server handler error disclosure; this application only uses gRPC clients for HCS. PostCSS findings concern CSS stringify XSS and attacker-controlled source-map path/file reads; the app serves repository-built styles and exposes no CSS or source-map processing endpoint. The `ws` findings concern HTTP/WebSocket server handling and frame-memory exhaustion; the app does not create a WebSocket server or invoke Node `ws` clients. The browser bundle scan passed on 197 generated assets and does not include the server-only Hiero SDK. The Hiero SDK's current exact gRPC pin has no compatible upstream patch identified in the current/latest 2.89.1 metadata. The PostCSS/npm suggested fix requires moving Next to v16, not adopted in this scoped review.
- **Development-only entries:** `@ethersproject/providers@5.7.2/5.8.0`, `@fastify/busboy@2.1.1`, `@next/eslint-plugin-next@15.5.27`, `@typescript-eslint/{eslint-plugin,parser,type-utils,typescript-estree,utils}@8.27.0`, `adm-zip@0.4.16`, `axios@0.21.4`, `braces@3.0.3`, `chokidar@3.6.0`, `eslint-config-next@15.5.27`, `fast-glob@3.3.1/3.3.3`, `globby@10.0.2`, `hardhat@2.22.19`, `hardhat-deploy@1.0.4`, `hardhat-deploy-ethers@0.4.2`, `hedera-harness@1.2.2`, `lint-staged@15.5.2`, `micromatch@4.0.8`, `mocha@10.8.2`, `serialize-javascript@6.0.2`, `solidity-coverage@0.8.17`, `tmp@0.0.33`, `undici@5.29.0`, and `zksync-ethers@5.11.2` are marked `dev` in the lockfile. These findings include archive allocation/extraction, HTTP/SSRF and decompression, glob-pattern exhaustion, temporary-file path handling, and build/test dependency aggregates. They are not shipped in the browser app and are only used by development/build/test tools here; do not feed untrusted archives or inputs to those tools.

The lockfile `npm audit` report lists package entries and aggregated transitive paths, so one underlying advisory can appear on parent and child packages. The exact installed versions, affected ranges, advisory titles, and npm fix suggestions were inspected from the JSON report. npm offered no compatible one-step fix for the critical Ethers v5 chain; the candidate fixes for development tooling involved toolchain releases or majors. No production-reachable high advisory with a demonstrated vulnerable application operation and a validated compatible fix was identified, so no dependency overrides or broad upgrades were made.

No critical/high advisory was found to be exploitable through the validated production browser or server request paths. The critical Ethers v5 chain is tooling-only, while the remaining runtime transitive findings require server or processing functions the application does not expose. Therefore these findings do not block M11 under the project's reachability criteria, but they remain dependency risks and must not be represented as remediated. Re-run `npm audit` and review exact dependency paths on each release, especially before changing wallet transports, adding server endpoints, or upgrading the Hiero SDK.
