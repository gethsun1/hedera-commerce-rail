## 2026-10-03 — Milestone 3: Native HBAR payment escrow

- **Reconnaissance:** Rechecked repository status/history, architecture/roadmap, Hardhat package, test conventions, deployment scripts, Solidity compiler, dependency versions, and fork test command. Existing `HtsTokenCreator` uses the HTS precompile at `0x167`, but its tests are fork-specific and its sample creation flow is not reused for payment settlement. Added no dependency.
- **Official Hedera pattern review:** Hedera's [EVM denomination reference](https://docs.hedera.com/hedera/sdks-and-apis/sdks/smart-contracts/ethereum-transaction) distinguishes EVM-visible tinybars (8 decimals) from Ethereum transaction `value` weibars (18 decimals); the official [Hardhat and Ethers tutorial](https://docs.hedera.com/hedera/tutorials/smart-contracts/hscs-workshop/hardhat) explains JSON-RPC `EthereumTransaction` submission and the `10^10` conversion. The [Solidity workshop](https://docs.hedera.com/hedera/tutorials/smart-contracts/hscs-workshop/solidity) demonstrates payable `msg.value` receipt and events. Hedera's documented Hardhat setup uses the network's JSON-RPC endpoint and chain ID; this repository's existing Testnet config (chain ID 296, explicit RPC and key) is retained. Existing 0x167 code is recorded as the later HTS extension reference only; no HTS transfer path was added or assumed safe for escrow here. HCS logs are not part of canonical contract state, and later Mirror Node indexing can consume the emitted EVM logs.
- **Contract design:** Added `PaymentEscrow` in the established contracts directory. Each agreement is HBAR-only (`asset == address(0)`), created unfunded, funded exactly once by its payer, and finalized by release or refund. Payer or configured arbiter can release; payer can refund only strictly after deadline; arbiter can refund as dispute resolution. Funding is rejected at/after deadline. There is no cancellation, milestone logic, HTS transfer, HCS write, frontend, or deployment execution. Events expose payment ID, parties, amount, asset marker and relevant timing. `PaymentEscrow` is tagged for explicit Hardhat deployment.
- **Security model:** Uses the already installed OpenZeppelin `ReentrancyGuard`; updates state and tracked liabilities before checked external value transfer, relying on transaction revert to restore state if the recipient rejects. Invalid IDs/addresses/amounts/deadlines, unauthorized actors, incorrect value, invalid state transitions, and direct unaccounted deposits revert with custom errors. `totalEscrowed` tracks funded liabilities; forced surplus cannot be treated as escrow liability. Arbiter is trusted to resolve a payment honestly and must be selected accordingly.
